# portscanner

一个用 Python 写的端口扫描器（学习项目）。

## 环境要求

- **Python 3**（开发环境：Python 3.14.4 / WSL Ubuntu）
- **无需安装任何第三方库** —— 只用标准库 `socket` / `sys` / `json` / `os` / `datetime` / `threading` / `queue`
- 跨平台：Linux / macOS / Windows 均可

## 用法

    # Linux / macOS 
    python3 scan.py <目标IP> <起始端口> <结束端口>

    # Windows（通常只有 python 这个命令）
    python scan.py <目标IP> <起始端口> <结束端口>

例子：

    # 扫描 1-1024
    python3 scan.py 192.168.75.128 1 1024

    # 只扫一个端口（起始和结束填同一个数）
    python3 scan.py 192.168.75.128 80 80

输出：

    开放： [22, 80]
    关闭数： 98
    超时数： 0
    结果已保存到：output/scan_192_168_75_128_20261018_133639.json

每次扫描的详细结果（含完整端口列表）会同时写入 `output/` 下的 JSON 文件，
文件名格式 `scan_<IP>_<时间>.json`，不会互相覆盖。

### 参数说明

- 三个参数之间**用空格分隔**
- 只扫单个端口时，**起始和结束填同一个数**
- ⚠️ 参数不足 / 端口不是数字时，会给出提示并退出

## 原理

对每个端口尝试建立 TCP 连接（下表为 Linux / WSL 的返回码）：

- 返回 0    → 端口开放
- 返回 111  → 端口关闭（对方回 RST）
- 返回 110  → 超时（被防火墙过滤）
- 返回 113  → 主机不可达

> ⚠️ **Windows 的返回码不同**（`10061` / `10035` / `10065`），详见下方「已知问题」。

### 并发模型

扫描是 **I/O 等待型**任务：大部分时间花在等对方回包，CPU 在等待时是闲着的。

实现用「**共享队列 + 固定线程池**」：

1. 所有端口放进 `queue.Queue()`
2. 启动 50 个线程，每个线程循环「取一个端口 → 扫描 → 写结果」
3. 队列空了线程就退出；主线程 `join` 等全部结束后汇总

不做「静态平均分片」的原因：**端口耗时不均** —— 关闭端口几毫秒就返回，
超时端口要等满 2 秒。按数量平均分会导致部分线程早早干完、部分线程拖到最后，
整体耗时取决于最慢那个线程。

## 性能

实测环境：WSL Ubuntu，目标为局域网内 VMware 虚拟机。

| 场景 | 单线程 | 多线程（50 线程） | 加速 |
| --- | --- | --- | --- |
| 1-1000 端口 | 9.6 秒 | 1.17 秒 | **8.2 倍** |
| 1-65535 端口 | 未实测（按 1-1000 推算约 10 分钟） | **9.4 秒** | — |

并发不是越多越好：线程数超过网络承受能力后，瓶颈会从「等待」变成「排队」，
再增加线程只会更慢（还容易触发目标防护）。拐点在哪，需要实测。

## 已知问题

### 1. Windows 下超时机制失效

在 Windows 上，一旦设置了 `s.settimeout()`，
`connect_ex()` 对**关闭的端口**会**一直等到超时**才返回，
而不是立刻返回"连接被拒绝"。

**实测对比**（同一目标、同一端口）：

| 环境 | 返回码 | 含义 | 耗时 |
| --- | --- | --- | --- |
| Linux / WSL | `111` | ECONNREFUSED（确定关闭） | 立刻 |
| Windows（**不设** timeout） | `10061` | WSAECONNREFUSED（确定关闭） | 立刻 |
| Windows（**设了** timeout） | `10035` | WSAEWOULDBLOCK（**还没完成**） | ⚠️ 等满超时 |

**原因**：`settimeout()` 会把 socket 变成非阻塞模式，
而非阻塞 `connect` 立刻返回"还没完成"；
Windows 上没有把该 socket 报告为可写，导致一直等到超时。

**影响**：在 Windows 上扫描时，每个关闭的端口都要等满 timeout，速度大幅下降。

**现状**：多线程已完成，但这个根因**没有解决** —— `scan_port()` 里仍然设了 `settimeout(2)`。
多线程把影响从「串行等」变成「并行等」，Windows 上扫全端口仍然慢，但不会像单线程那样需要几十小时。

**计划**：给 Windows 单独一条路径 —— 不设 timeout，改用 `select` 判断 socket 是否可写。

### 2. 端口状态区分不够细

目前只区分「开放」和「非开放」，实际上：

- `111` / `10061` → **确定关闭**（收到 RST）
- `110` / `10035` → ⚠️ **超时** —— 可能是关闭，也可能是**被防火墙过滤**

更专业的做法是分开报告「关闭」和「过滤」（nmap 就是这么做的）。
